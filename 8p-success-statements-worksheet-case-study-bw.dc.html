Success Statements

Renovation Revolution

Success Statements are a single, short sentence that shows the impact of what you did. They should not be longer than a resume bullet, 180-300 characters. This is the format:

The Format
“I improved this thing by this measurable amount using this method.”

We’ll do each section of the format separately, then combine them. All of the examples use Renovation Revolution. Let’s pretend the app is up and running, because most of you are adding to existing projects. In this scenario, my goal for the quarter was to add a new vendor to the app.

01

Thing You Improved

Find everything you completed. No format yet, this is brainstorming. Write down the project name and your role or a feature/bug on that project. This is only the "what" you did; we'll get into the technical details (the "how") in the next section. Look through your tickets, merged pull requests, design docs, emails, and chat messages. One item per line; you can repeat a project if there were multiple major features this quarter. If you want to include minor features, we will roll them up later. If you use the AI prompt, replace the examples with your own data sources and ensure they are connected via an MCP, skill, or direct connection.

AI Prompt
“You are a software engineer compiling all the work you did over the last 90 days. Connect to these sources directly: code repository [GitHub, GitLab], ticketing system [Jira, Linear], design docs [Google Docs, Confluence], email [Outlook, Gmail], and chat [Slack, Teams]. My role is [title] on the [team] team, covering [date range]. Merge everything into a single list of work, removing duplicates where the same effort appears in more than one tool. Group it into projects, and for each project write one line naming it and my role in it. Note which items lack evidence of the outcome, and suggest a source you could check for what is missing.”
Example
◆Reviewed vendor technical offerings
◆Designed a connection from their catalog to our app
◆Created a service to poll their catalog, match their items to our taxonomy, and review products for missing data
What I worked on
Projects, roles, features, bugs
02

Method You Used

Now that you have some projects, let’s dive into the details. For each item, fill in how you solved the problem. Include all technical details; we'll edit and roll up similar items later. I think you will be surprised by how much you have accomplished.

Example
◆Built a custom REST API connector for the vendor’s legacy SOAP-based product catalog system
◆Implemented an OAuth 2.0 authentication flow with token refresh and secure credential storage
◆Created a data transformation layer mapping the vendor’s product schema to our standardized format
◆Built a webhook listener for real-time product updates (pricing, availability, specifications)
◆Implemented rate limiting and retry logic handling vendor API constraints (100 requests per minute)
◆Added a fallback to daily batch sync when real-time updates failed
◆Added data quality validation, rejecting incomplete or malformed product records
The technical detail
What you actually built, integrated, tested, or fixed
03

Measurable Amount

Impact should be shown in terms of time or money. It could reduce costs or increase profits. Labor is a considerable cost, so saving time is just as good as saving money. Did you add a feature that brought in more sales? Or reduced manual work for the sales team? Or for the customer service team, allowing them to take more calls per hour? Did you eliminate bugs to reduce churn? It can be challenging to obtain exact numbers, so you can use estimates (~10% of users). You might need to consult with other teams to acquire impact numbers. Let your boss know if you’re going to talk to anyone you don’t normally interact with.

Example
◆Added 2,400 products to our items catalog, expanding it by 18%
◆Increased offerings increase customer spend
◆Customer spend on vendor products grew roughly $10,000 during the pilot
Who to ask: Sales operations owns the pilot revenue figure. Support owns the churn rate for plumbing products.
Who can I ask about the impact?
The impact
Numbers, estimates, and percentages
04

Success Statements

Finally, time to write your Success Statements! Here is the format again:

The Format
“I improved this thing by this measurable amount using this method.”

You might need to combine or summarize actions to match the format. Make sure the method is understandable to anyone at the organization; they might not understand all the technical jargon or even the projects you work on. I have included an AI prompt, but with this specific format, it can be easier to write it yourself. The more you practice, the better you’ll get at writing these.

AI Prompt
“You are a software engineer compiling all the work you did over the last 90 days into Success Statements. Here is the raw data [paste your lists from the sections above]. Write Success Statements in this format: “I improved this thing by this measurable amount using this method.” A Success Statement is a single short sentence (no longer than a resume bullet point) that shows the impact of what I did, in language anyone can understand. Keep the method free from jargon and never invent data or numbers. Cite your Success Statements from the data I provided or data you are connecting to. Roll up related items into one statement. There can be many statements for a project, but one major change has more impact than multiple minor changes. Return one statement per line with the most impactful or interesting first. Highlight any data that could not be used because it did not have the information needed to fit the format, like a missing method or a measurable amount.”
Example
◆“I increased the product catalog by 18% and generated $10,000 in pilot sales through an automated sync with the new vendor.”
◆“I reduced duplicate and incomplete products on the UI for the plumbing pipes vendor, decreasing customer churn for their products 10%, using a new data validation service.”

◇

Make It A Habit

You already write down what you did before standup. Keep those notes in a running document instead of throwing them away. Review the document weekly and mark anything that could become a Success Statement. Another option is to include Success Statements on your task tickets. For each feature, you will need to find a way to capture the impact. This will save you time later and help you determine if you’re on the right track. If you didn’t have any impact, maybe you are not prioritizing correctly.
