Failure Audit

This worksheet will help you audit all of your service's dependencies. You want to know who owns them and what happens when it fails. Most teams find at least one dependency where the honest answer is "nobody knows." This lets you both gracefully degrade service and accurately triage support questions by routing them to the correct service owner. Do this before you run any chaos experiments to help you have a hypothesis to test against.

Dependency Inventory

02

Current Behavior

For each one, write what your service does today when that dependency stops responding. Hangs, returns a 500, retries forever, and "I don't know" are all valid answers. Do not guess and do not write what you hope it does.

◇ AI Prompt
"You are a backend engineer helping me audit one service for dependency failures. Here is the service: [paste the code that makes outbound calls, plus any client, timeout, retry, and connection pool configuration]. For every outbound call you find, tell me what this code actually does when that dependency stops responding: hangs, returns an error to the caller, retries, or falls back. Quote the line or setting that decides it. Where the code does not settle it, say 'not determined by this code' and name the library default or config file I need to check myself. Return one row per dependency with four columns: dependency, what happens today, the evidence, and what I still need to verify. Do not suggest fixes yet."
