Backend
Technical Decisions

Renovation Revolution

You have just been hired as the backend tech lead for Renovation Revolution. There are many decisions to be made before you even start designing. Remember the structure we learned in Chapter 3? Using the criteria of popularity, fit, and cost can help you narrow down the seemingly infinite technical choices. I have broken down the technical choices into logical groups to make it easier to tackle them one at a time. I have also filled in suggested answers. Practice your decision-making by agreeing with me or changing the answers.

AI Prompt
"I am starting a backend for [describe the product]. Walk me through the key early decisions for requirements, technology, architecture, security, deployment, and workflow, and flag the ones that are hardest to change later."
1

Requirements & Planning

What are the expected data volumes and traffic levels?
Example: Moderate volume with spikes on weekday evenings and during spring and summer renovation season. Autoscale on CPU with headroom to spin up instances before the spikes.
Are there any regulatory or compliance requirements (e.g. GDPR, CCPA, PCI DSS)?
Example: Not a regulated industry, but we store personal information and handle payments, so follow GDPR and CCPA for user data and PCI DSS for payments.
2

Technology Choices

Which programming language and backend framework best fit the project?
Example: Python with Django. The team already knows Python, and Django gives us a mature ORM, built-in admin, and authentication out of the box so we can ship features instead of wiring up plumbing.
What database technology will be used (SQL, NoSQL, in-memory)?
Example: PostgreSQL, a relational SQL database, for structured project, contractor, and selection data. Add Redis for caching later as we scale.
What API architecture will be implemented (REST, GraphQL, gRPC)?
Example: GraphQL, so the web and mobile clients can each request exactly the data they need in one call. It is more modern than REST and avoids the over- and under-fetching REST runs into as pages get complex. Consider gRPC for internal service-to-service calls.
3

Architecture & Design

How will the backend be structured (monolith, microservices, serverless)?
Example: Start as a modular monolith and split out services only where scaling actually demands it.
What will the data models and relationships look like?
Example: Users, Projects, Rooms, Images, Quiz Results, and Selections, as mapped in the data modeling worksheet.
How will scalability and performance be addressed from the start?
Example: Design for horizontal scaling. Plan where caching and indexes will go, but do not optimize prematurely.
4

Security & Authentication

What authentication and authorization mechanisms are required?
Example: Role-Based Access Control (RBAC) with a small set of roles: customer, contractor, vendor, and admin.
How will sensitive data be stored and transmitted securely?
Example: Encrypt data in transit and at rest using a vetted library. Never roll our own encryption.
What security best practices need to be enforced (input validation, error handling, rate limiting)?
Example: Input validation, safe error handling, and rate limiting built in from day one.
5

Deployment & Operations

Where will the backend be hosted (cloud provider, on-premises)?
Example: AWS. A major public cloud gives us managed autoscaling and databases so we do not maintain hardware, and it is easy to hire engineers with common AWS skills.
How will deployment, monitoring, and logging be set up?
Example: Automated CI/CD with GitHub Actions for low-downtime deploys and easy rollback. Ship metrics, logs, and traces to a hosted observability tool from day one.
What is the backup and disaster recovery plan?
Example: Automated daily backups of the PostgreSQL database with point-in-time recovery, plus a restore drill each quarter so we know it actually works.
6

Collaboration & Workflow

What is the version control and branching strategy?
Example: Git with short-lived feature branches and reviewed pull requests.
How will tasks, issues, and documentation be tracked and managed?
Example: A ticketing system for work, plus living documentation kept somewhere everyone can find it.
Who are the key stakeholders and points of contact for project decisions?
Example: Product for the customer voice, DevOps for infrastructure, plus vendor and contractor partners.
